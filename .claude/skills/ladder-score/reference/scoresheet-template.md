# 採点結果の書式

```markdown
# 採点 — <対象> / <期間>

## 点

| A 上流・提案 | B 型の運用 | C ドメイン | D 検証 | E 基盤 |
|---|---|---|---|---|
| L3 | L4 | 未観測 | L2 | L2 |

## 根拠

### A 上流・提案と関係者調整 — L3

- **L3 真**「性能・運用・移行の欠落を要件に対して指摘できる」
  — #142 のレビューで、移行時のデータ欠落を実装前に指摘している
- **L4 偽**「提案資料と見積の根拠を自分で組める」
  — 提案資料が成果物に出てこない

### C ドメイン理解 — 未観測

- 判定に使える成果物が期間内に無い。設計資料を書く作業が回っていない

## 落とした判定文

- D の L3 — `docs/guarantees.md` がリポジトリに無い。保証を列挙する置き場が無いため、
  誰に対しても偽になる。台帳を敷いてから採り直す

## 次に上げる1軸

**D 検証・品質保証（L2 → L3）**

- 回す手順: 保証台帳を敷き、担当領域の公開面を列挙させる
- 次の採点で読むもの: `docs/guarantees.md` とテストの対応
```

## 書くときの規則

- 点は軸ごとに独立して出す。合計も平均も出さない
- 真偽の根拠は、ファイルパス・PR 番号・コミットのいずれかで引く
- 偽と判定した軸は、**どの判定文で止まったか**まで書く。止まった位置が次に上げる先になる
- 人格や態度に触れない。判定文にある事実だけを書く
