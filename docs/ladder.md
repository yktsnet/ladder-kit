# ラダー

このリポの正本である。採点・育成・選考はすべてこの表を読む。

物差しは5軸と5段階でできている。軸は測るもの、段階は依頼元に対してどこまで一人で
任せられるかの刻みである。

判定文は、**リポジトリの何を開けば真偽が確かめられるか**が分かる形で書いてある。
「自律的に」「複雑な」のような、評価者の解釈に委ねる語は使わない。

判定文が名指しする置き場は [sdlc-kit](https://github.com/yktsnet/sdlc-kit) のものである。
別の型を使っているなら、その型の置き場へ読み替える。

## 段階

| Lv | 委任範囲 |
|---|---|
| L1 | 標準化の外。単位作業を指示され、成果物はレビューで書き直される |
| L2 | 標準化されたワークフローを理解し、単位作業をレビュー前提でやり切る |
| L3 | 担当領域を自走する |
| L4 | 案件の一領域を依頼元との接点ごと持ち、進捗と品質を自分で管理する |
| L5 | 案件全体の設計・推進を担い、依頼元の課題設定に関与する。得た型を他の案件へ渡す |

**L1 は標準化の外に置いてある。** 型を渡しても回せず、個人の書き方で成果物を出す状態が
ここに当たる。L1 から L2 への遷移は、型を渡して回させれば埋まる区間である。

**L2 は、配られた型を理解すれば到達する点である。** 判定文は型が実際に強制するものだけで
書いてあり、理解した人が L2 に届かないなら、判定文か型のどちらかが間違っている。

**この保証が効くのは L2 までである。** L3 以上は5軸とも、型を回した経験の副産物では
届かない。C ドメイン理解は L2 の時点で外れる。依頼元の業務を成果物に落とす手順を
持つ型が少ないためで、そこは型の側の欠落になる。

**L5 の行は到達像である。** 5本の判定文がすべて真になる人を探すためではなく、
どの軸がどれだけ足りないかを言うために読む。

報酬帯との対応は持たない。段階と報酬の結び付け方は各社で違い、物差しの側に固定すると
持ち込めなくなる。

## 軸

| | 軸 | 測るもの |
|---|---|---|
| A | 上流・提案と関係者調整 | 要件を引き出し、完了条件と非機能を定める。依頼元と社内の非開発者に対する説明と調整 |
| B | 標準化されたワークフローの運用 | 配られた型の運用。回せる、選べる、直せる |
| C | ドメイン理解 | 依頼元の業務と現行システムの把握、および関係者間での共有 |
| D | 検証・品質保証 | 何を確かめれば正しいと言えるかの設計 |
| E | インフラ・基盤 | 環境とパイプラインの構築、構成の選定とリポジトリ全体の管理 |

推進力・当事者意識のような態度の軸は持たない。進捗管理と期待値調整は A、
型の規律と仕組みへの反映は B に収まり、独立の軸として残る中身が無い。

**B が、エージェントで開発を回すチームに固有の軸である。** 生成そのものの巧拙ではなく、
配られた型に乗れるかを測る。他の4軸は既存の公開ラダーと重なる。

## A 上流・提案と関係者調整

| Lv | 判定文 | 読むもの |
|---|---|---|
| L1 | 渡された要件をそのまま着手する。曖昧さは実装が止まる形で表面化する | 着手後に要件を問い直した回数 |
| L2 | `PLAN.md` に出口と順序を書ける。完了条件が書けないことで、要件の曖昧さが着手前に自分に見える | `PLAN.md` の出口の節 |
| L3 | 性能・運用・移行の欠落を要件に対して指摘できる。担当領域の設計を非開発者に読める資料にでき、課題を先出しして進捗を自分で管理する | 設計資料、Issue や PR の課題提起 |
| L4 | 依頼元への提案資料と見積の根拠を自分で組める。営業など社内の非開発者と要件を共有し、案件全体の課題管理と期待値調整ができる | 提案資料、見積の内訳 |
| L5 | 依頼元の課題設定に関与し、提示された要件を組み替えて提案できる。複数案件にまたがる関係を作れる | 提案の採否と、要件が組み替わった記録 |

## B 標準化されたワークフローの運用

| Lv | 判定文 | 読むもの |
|---|---|---|
| L1 | 型を渡されても回せず、個人の書き方で成果物を出す。詰まったことは聞かれてから報告する | 差し戻しレビューの回数 |
| L2 | 指示された手順を回し、標準の形の成果物を出せる。変更1本ごとに区切り、コミットで止まって裁可を待てる | 直近の PR の粒度、裁可の残り方 |
| L3 | 作業に対して回す手順を自分で選べる。他の作業者の成果物を読んで自分の進め方を直せる。型が噛み合わない作業を見分けて手で進める判断ができる | 手順を外した作業と、その理由の記録 |
| L4 | 既存の型の欠落を特定して直せる。無い手順を作る要否を判断し、要ると見れば自分で作ってチームに使わせる | `docs/ops/` への変更と、その後の利用 |
| L5 | 案件横断で型の構成を設計し、他人が回せる形に配布できる。詰まりの型を拾って仕組みの側へ反映できる | 他案件への配布と、配布後の定着 |

**L3 の「他の作業者の成果物を読んで自分を直せる」は、受け取る側の能力である。**
公開ラダーはメンタリングやレビューという与える側だけを測ることが多いが、
型が配られている環境では、横を読んで自分に取り込めるかが先に効く。

**L4・L5 は道具の利用者から作者への移行である。** 判定文は「作れる」ではなく、
要否を判断した上で仕組みへ戻せるか、という形にしてある。作らない判断も能力に含む。

## C ドメイン理解

| Lv | 判定文 | 読むもの |
|---|---|---|
| L1 | 担当した機能の範囲しか知らない。前後の業務フローを聞かれても答えられない | 設計時の質問の範囲 |
| L2 | 担当機能の前後の業務フローを説明できる | 設計資料の前提の節 |
| L3 | 現行システムの全体構成と、業務上の例外処理の在処を把握している | 影響範囲の見積もりの精度 |
| L4 | 依頼元の業務の矛盾や非効率を指摘できる。ドメインの理解を依頼元と開発者の間ですり合わせ、双方が同じ言葉で話せる状態にできる | 用語集、議事の指摘 |
| L5 | 複数案件のドメインを横断し、共通化できる業務の型を示せる | 複数案件に渡った設計 |

## D 検証・品質保証

| Lv | 判定文 | 読むもの |
|---|---|---|
| L1 | 動いたことを確認の完了とする | PR の検証手順の節 |
| L2 | 完了条件に「何を読んで確認するか」を書ける。機械で確かめられない変更でも確認手段を言葉にできる | PR の検証手順の節 |
| L3 | 担当領域の公開面に対する保証を列挙し、テストの欠落を指摘できる | `docs/guarantees.md` とテストの対応 |
| L4 | 案件の非機能要件を検証計画に落とし、リリース判定の基準を決められる | 検証計画、リリース判定の記録 |
| L5 | 案件横断で品質基準を定め、他人の検証設計をレビューできる | 他案件へ渡した基準 |

## E インフラ・基盤

| Lv | 判定文 | 読むもの |
|---|---|---|
| L1 | 用意された環境の上でだけ作業する。手元で動くことと、環境に載ることの区別が付かない | CI の失敗履歴 |
| L2 | リポジトリの CI 定義とブランチ保護を読み、壊さずに変更を通せる | CI の失敗履歴、force-push の有無 |
| L3 | 担当領域の CI/CD と検証用環境を自分で組める | ワークフロー定義の変更履歴 |
| L4 | 案件のインフラ構成を選定できる。クラウドとサービスの選択をコストと運用性で説明でき、リポジトリ全体の構成を管理できる | 構成の選定資料 |
| L5 | 案件横断で基盤の型を作り、他案件へ配布できる | 他案件で使われた基盤 |
