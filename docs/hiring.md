# 候補者に当てる

在籍者と同じ軸・同じ段階を使う。**替えるのは証拠源だけである。**

別のルーブリックを立てると、換算表を保守することになり、換算の妥当性を誰も確かめられない。
補充は育成で届かない分を埋める行為なので、在籍者と候補者を同じ物差しの上に並べられないと、
そもそも判断ができない。

## 証拠源の対応

| 軸 | 在籍者 | 候補者 |
|---|---|---|
| A 上流・提案 | `PLAN.md`、設計資料、提案資料 | 直近の案件で、要件のどこを自分で決めたか。決めた根拠を聞く |
| B 型の運用 | PR の粒度、裁可の残り方、`docs/ops/` への変更 | **測れない。**下記 |
| C ドメイン | 設計資料の前提、用語集 | 前職の業務を、開発者でない人に説明させる |
| D 検証 | `docs/guarantees.md`、PR の検証手順 | 直近で壊した障害と、その後どこを確かめるようにしたか |
| E 基盤 | CI の失敗履歴、ワークフロー定義 | 組んだ環境の構成と、選定理由をコストと運用性で聞く |

**成果物を持ち込ませない。** 前職のリポジトリは出せないのが普通で、出せる人だけが
有利になる。判定文は自社の置き場を名指ししているので、そのまま当てず、
上の対応で聞き取りへ翻訳する。

## B 軸だけは入社前に測れない

判定文が、配られた型の運用そのものだからである。渡されていない人には真になりようがない。

見るのは現在地ではなく、**渡したら乗れるかの見込み**になる。経歴から聞けるのは次の形。

- 既にある規約や手順に、自分のやり方より先に合わせられたか
- 作業を区切って、途中で確認を挟んでいたか
- 手順が噛み合わないとき、黙って外したか、外す理由を言ってから外したか

乗れないと見れば **L1 として扱う。**判定が空欄になるわけではない。L1 は標準化の外にある
段階なので、取るなら配置の側で受ける前提になる。

## 課題を出すなら、型を渡して回させる

コーディング課題で B 軸を近似したいなら、問題を解かせるのではなく、
**手順書を渡して、その通りに1本通させる。**見るのは出力の出来ではなく、

- 手順書を先に読んだか
- 変更を1本に区切ったか
- 確認を求めるべき箇所で止まったか

エージェントを使ってよいと明示する。使わせないと、測りたい軸と違うものを測ることになる。

## 入社後に採り直す

候補者の点は見込みを含む。**入社後、型を回した成果物が出た時点で採り直す。**
特に B は、見込みと実測がずれる前提で置いてある。

ずれ方が同じ方向に続くなら、聞き取りの側を直す。

## 取る前に決めておくこと

- **どの軸の欠けを埋めるために取るのか。** 在籍者を採点していれば、最も低い軸が分かっている。
  そこを埋める人を探すのか、既に高い軸をさらに伸ばす人を探すのかで、見る軸が変わる
- **未観測を許すか。** 面接で埋まらない軸は未観測のまま残す。埋めるために点を下げない
