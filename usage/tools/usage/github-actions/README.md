# GitHub Actions の分数

組織の private リポジトリが使った GitHub Actions の分数を日ごとに集め、月の無料枠と予算に収まるかを見る。
収まらない見込みが出たら、月の途中で CI の組み方を直すか、予算を上げるかを決める。

このページは月全体の見込みを示す。ワークフローごとの週の推移は [workflows.md](workflows.md) にある。
どちらも定時に作り直す。時刻は [tools/usage/README.md](../README.md#仕組み) の「仕組み」にある。

## 分数を抑える書き方

| 書き方 | 見るところ | できている状態 |
|---|---|---|
| Issue やコメントの操作で起動しない | workflows.md の「起動のきっかけ」 | `issues`・`issue_comment` が上位に無い。集計のような処理は、日次の定時実行（`schedule`）にまとめている |
| ランナーの上で待たない | workflows.md の「1回あたりの分数」 | 中身に比べて長いワークフローが無い。`sleep` や、ほかの処理の完了待ちをランナーの上でしていない |
| PR と main への push で同じ検査を重ねない | workflows.md の「起動のきっかけ」 | 同じワークフローが `pull_request` と `push` の両方で上位に並んでいない |
| 数十秒で終わるジョブを分けない | workflows.md の「1回あたりの分数」 | ジョブは1つごとに1分単位で切り上がるので、短いジョブは1つにまとめている |

## 予算を超える見込みが出たら

月末の見込みが 15 ドル（予算）の段を超えたら、次の順に進める。

1. workflows.md の「分数」で、週ごとに増えたワークフローを探す
2. 同じワークフローの「回数」と「1回あたりの分数」で、増えたのがどちらかを見分ける
   - 回数が増えた：PR の本数が増えた。開発のペースによるもので、無駄ではない。予算を上げるか、1回あたりの分数を削るかを決める
   - 1回あたりの分数が増えた：テストやダミーデータが増えて、ジョブが長くなった。ジョブのステップごとの時間を見て、長くなったステップを探す
   - 前の週に無かったワークフローが出た：新しく足したものである。上の「分数を抑える書き方」に当たらないかを見る
3. 見分けた結果と決めた対応を、Issue に残す
