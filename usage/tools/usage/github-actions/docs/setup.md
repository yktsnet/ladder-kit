# 集め方と設定

分数をどこから集め、表とグラフをどう作り直しているかと、集められないときの直し方を書く。運用する人向けである。表の見方は
[README.md](../README.md) にある。

## 何が集まるか

組織の private リポジトリの、GitHub Actions の実行記録から数える。Billing の画面と API は
組織の Owner でないと読めないので、使わない。

## ファイルと取り方

| ファイル | 中身 |
|---|---|
| `collect.py` | 実行記録から日本時間の1日単位で分数を取り出し、`data/` に置く |
| `render.py` | `data/` から `charts/` のグラフ、`README.md` の表、`workflows.md` を作り直す |
| `data/` | 日ごとの分数。リポジトリ・ワークフロー・起動のきっかけごとに、回数と分を記録する |
| `workflows.md` | ワークフロー別の週ごとの分数。`render.py` が作り直す |

`collect.py` は、先月の1日（環境変数 `ACTIONS_FIRST_DAY` で変えられる）以降で `data/` に無い日、読めないリポジトリが残っている日、直近4日を取る。実行記録は消えないので、
止まっていても次の実行で埋まる。直近4日を取り直すのは、日付の変わり目に走っていた実行が、
定時の実行の時点ではまだ終わっていないためである。日曜と月曜は定時の実行が無いので、火曜の実行が金曜の分まで
取り直せる日数にしている。

`collect.py` は、`.github/workflows/usage.yml` が渡す Secret `ORG_READ_TOKEN` の token で実行記録を読む。token に要る権限は
[tools/usage/README.md](../../README.md#token-を作る) の「token を作る」にある。

## 読めないリポジトリがあるとき

token で実行記録を読めないリポジトリ（HTTP 403・404）があると、`collect.py` はそのリポジトリを飛ばして残りを書き、
最後に失敗で終わる。ワークフローは続けて表を作り直してコミットするので、ジョブは赤になるが、読めたリポジトリの分は反映される。

- 読めなかったリポジトリは、`data/<日付>.json` の `unreadable` に残る。その日のそのリポジトリの分は、前に取れていた分のまま残す。
  前の記録が無ければ 0 分になる
- `README.md` の表の上に、今月読めなかったリポジトリの名前が出る
- token の権限を直せば、次の定時実行で埋まる

全リポジトリで読めないときは、token に Actions の権限が付いていない。一部のリポジトリだけなら、
token を作った人にそのリポジトリが見えていない。どちらも直せるのは token を作った人である。

## 手元で取り直す

1日分を取り直すときは次のように流す。

```bash
GITHUB_ORG=<組織> ORG_READ_TOKEN=$(gh auth token) python3 tools/usage/github-actions/collect.py --date 2026-11-03 --force
python3 tools/usage/github-actions/render.py
```

手元の token から見えないリポジトリは一覧に出ないので、`unreadable` にも載らずに分数から抜ける。手元では、
全リポジトリが見える人の token で流す。

1日分を取るたびに、リポジトリの数と実行の回数に応じて GitHub API を呼ぶ。数十のリポジトリで1か月分を取り直すと、数千回になる。個人の token は1時間に5,000回までなので、
続けて流すと上限に当たる。
